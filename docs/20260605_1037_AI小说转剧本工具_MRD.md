# AI 小说转剧本工具 MRD

文档版本：v1.0  
创建时间：2026-06-05 10:37  
项目代号：Novel2Script

## 1. 市场概述

AI 写作工具已经从通用文本生成走向垂直创作流程。小说作者、短剧团队和内容工作室不仅需要“生成一段文字”，还需要工具理解角色、章节、场景、冲突和叙事节奏，并输出能进入后续制作流程的结构化结果。

小说转剧本处在 IP 改编链条的早期阶段。它的商业价值来自两个方面：

- 降低改编初稿成本。
- 将非结构化小说转成可编辑、可校验、可追踪的结构化内容资产。

## 2. 市场机会

短剧、互动故事、广播剧、有声剧和动画分镜等内容形式对小说 IP 的消耗速度很快。传统人工改编流程需要编剧先读完原文，再整理人物、场景、冲突和剧情走向，随后才能进入剧本初稿。这个过程耗时且依赖经验。

Novel2Script 可以切入“改编初稿生成”这个低风险、高频、可演示的环节。它不直接承诺产出最终成片剧本，而是提供结构化底稿，让创作者更快进入人工打磨阶段。

## 3. 竞品与参考产品

### 3.1 Final Draft

Final Draft 是专业编剧软件，重点能力包括自动格式化、Beat Board、Outline Editor、修订评论、协作和生产拆解。它证明专业剧本工具重视结构规划和标准格式，但它主要服务人工编剧，不以小说自动改编为核心。

参考：https://www.finaldraft.com/products/features/

### 3.2 Sudowrite

Sudowrite 是面向小说作者的 AI 写作工具，提供写作、改写、头脑风暴、场景组织和章节草稿等能力。它证明 AI 写作市场对创作流工具有需求，但它更偏小说生成和辅助写作，不强调输出可校验剧本 Schema。

参考：https://docs.sudowrite.com/getting-started/dQph1snuwbfMWG9wRjsNug/features/dq7YUMNy5ZMvKUJiRAisyT

### 3.3 ScreenJSON

ScreenJSON 将剧本定义为开放结构化文档，支持转换、查询、渲染、LLM 输入和工具链消费。它证明剧本结构化是有长期价值的，但项目目标偏开放格式和工具链，不是中文小说到 YAML 剧本的端到端产品。

参考：https://screenjson.com/

### 3.4 NovelVids

NovelVids 使用小说管理、实体抽取、资产管理、分镜生成和视频合成流程，强调角色与场景一致性。它证明小说内容生产可以通过结构化流水线逐步进入视频化，但其范围比本实训项目大，短期内不适合作为完整目标。

参考：https://novelvids.com/

### 3.5 学术方案 R2

R2 论文指出小说转剧本存在幻觉、情节抽取不一致、因果链保持困难等问题，并采用 Reader/Rewriter 以及因果情节图思路。该方向可为本项目提供技术论证：先理解再改写，比直接让模型“一步生成剧本”更稳定。

参考：https://arxiv.org/abs/2503.15655

## 4. 差异化定位

Novel2Script 的差异化不在于成为全功能编剧软件，而在于：

- 面向中文小说改编场景。
- 输入 3 个章节以上长文本，输出 YAML 结构化剧本。
- 把 YAML Schema 作为产品核心资产。
- 通过校验器保证输出可解析、可编辑、可二次加工。
- 使用分阶段 AI 流程降低长文本幻觉和格式错误。

一句话定位：

面向小说作者和短剧创作者的 AI 结构化剧本初稿生成工具。

## 5. 用户画像

### 5.1 独立小说作者

目标：希望将自己的小说快速改编为短剧或广播剧初稿。  
痛点：不熟悉剧本格式，手动拆场景和对白耗时。  
需求：低学习成本、结果可编辑、能说明保留和改写了哪些情节。

### 5.2 短剧编导

目标：从小说中快速判断是否适合短剧化。  
痛点：前期读稿和拆稿工作重复，多个候选 IP 比较困难。  
需求：场景列表、冲突点、人物关系、对白密度、集数拆分建议。

### 5.3 内容工作室

目标：批量处理小说，形成可评估的结构化资产。  
痛点：非结构化文本难以进入项目管理和生产系统。  
需求：稳定 Schema、批量任务状态、导出能力、后续 API 扩展空间。

### 5.4 实训评审

目标：快速判断项目是否符合题目要求和工程能力。  
痛点：很多 AI 项目只是聊天套壳，缺少验证和闭环。  
需求：可运行 Demo、清晰文档、结构化输出、异常处理和设计解释。

## 6. 用户需求

高优先级：

- 支持粘贴或上传小说文本。
- 至少处理 3 个章节。
- 自动识别章节。
- 生成 YAML 剧本。
- 输出符合 Schema。
- 支持复制和导出。
- 展示生成过程和错误状态。

中优先级：

- 展示人物表、场景表和事件链。
- 支持局部重新生成。
- 支持 YAML 校验报告。
- 支持改编说明。
- 支持样例小说一键体验。

低优先级：

- 多人协作。
- 版本对比。
- FDX、Fountain、PDF 导出。
- 视频分镜或图片生成。

## 7. 市场进入策略

实训阶段：

- 重点做单机或 Web MVP。
- 使用自带样例小说保证 Demo 稳定。
- 通过 README、BRD、MRD、PRD、Schema 文档展示专业度。
- Demo 视频突出“从原文到可校验 YAML”的闭环。

后续阶段：

- 增加批量项目管理。
- 增加短剧集数拆分。
- 增加 Fountain 或 Markdown 剧本导出。
- 提供 API 给内容团队或自动化生产链。

## 8. 商业模式设想

短期不做商业化，实训目标优先。

长期可选模式：

- 免费额度 + 按生成次数计费。
- 面向工作室的项目席位订阅。
- 私有化部署，适合有版权敏感内容的机构。
- API 计费，服务短剧生产和 AIGC 内容平台。

## 9. 需求优先级

P0：

- 输入 3 章小说。
- 章节解析。
- AI 生成 YAML。
- YAML Schema 校验。
- 导出 YAML。
- Schema 文档。

P1：

- 人物和场景可视化。
- 局部重写。
- 改编总结。
- 生成质量评分。

P2：

- 多格式导出。
- 批量任务。
- 用户账号。
- 协作和评论。

## 10. MRD 结论

题目三的市场价值在于将“小说改编”从人工经验流程变成结构化、可校验、可扩展的 AI 工作流。对实训来说，它比实时语音题目更容易完成，也更容易通过文档、Schema、校验和 Demo 展示工程能力。MVP 应优先保证结构化输出质量，而不是扩展过多外围功能。
