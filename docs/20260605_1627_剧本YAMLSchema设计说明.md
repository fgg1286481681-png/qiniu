# 剧本 YAML Schema 设计说明

文档版本：v1.0  
创建时间：2026-06-05 16:27  
对应 Schema 文件：`backend/schema.json`  
适用项目：Novel2Script，AI 小说转剧本工具

## 1. 设计结论

当前没有检索到被广泛采用的“中文剧本 YAML 标准格式”。行业里更常见的是：

- Fountain：面向编剧写作的纯文本剧本标记格式，强调场景标题、动作、角色、对白、转场等剧本元素。
- ScreenJSON：面向剧本数据交换、分析和工具链处理的结构化 JSON 数据模型，强调可查询、可校验、可被程序消费。
- Final Draft FDX：专业编剧软件常用的剧本文档格式，但偏专有生态，不适合作为本项目三天实训的核心交付格式。

因此，本项目采用“自定义 YAML + JSON Schema 校验”的方案：YAML 面向创作者阅读和编辑，JSON Schema 面向程序校验和后续工程扩展。

## 2. 调研依据

### 2.1 Fountain

Fountain 是开放的纯文本剧本标记语言，核心元素包括标题页、场景标题、动作、角色、对白、括注、转场等。它的优点是轻量、易写、可被多种工具渲染为标准剧本格式。

本项目借鉴 Fountain 对剧本元素的划分，但不直接采用 Fountain 作为输出格式。原因是 Fountain 更适合人类直接写作和排版，而本项目要求输出结构化 YAML，且需要保留小说章节、人物 ID、地点 ID、事件来源、改编说明等机器可处理信息。

参考：[Fountain Syntax](https://fountain.io/syntax)

### 2.2 ScreenJSON

ScreenJSON 将剧本视为结构化语义文档，支持存储、查询、转换、分析和提供给 LLM 使用。它强调剧本不只是排版文本，还应包含结构化的场景、角色、正文元素、修订、注释等信息。

本项目借鉴 ScreenJSON 的“剧本即结构化数据”思想，但没有完全照搬其复杂模型。原因是本项目的输入是小说章节，目标是生成可编辑的剧本初稿，而不是处理成熟工业剧本的完整生产数据。

参考：[ScreenJSON](https://www.screenjson.com/)

### 2.3 YAML

YAML 本身是通用数据序列化格式，不提供专门的剧本语义。它适合表达层级数据，阅读体验比 JSON 更友好，但需要配合 Schema 才能保证结构稳定。

本项目使用 YAML 作为剧本交付文本，使用 `backend/schema.json` 进行结构校验。

## 3. Schema 设计目标

本项目的 YAML Schema 需要同时满足四个目标：

1. **符合题目要求**：能把 3 个章节以上小说转换成结构化剧本 YAML。
2. **适合中文小说改编**：保留章节来源、人物、地点、事件、场景、对白、动作、旁白和改编说明。
3. **便于人工编辑**：字段命名清晰，层级不过深，用户可以直接修改 YAML。
4. **便于程序校验**：所有关键对象都有 ID，场景引用人物和地点时可做一致性检查。

## 4. 顶层结构

完整 YAML 顶层包含以下字段：

```yaml
schema_version: "1.0"
metadata: {}
chapters: []
characters: []
locations: []
events: []
scenes: []
adaptation_notes: {}
```

设计原因：

- `schema_version` 用于后续兼容升级。
- `metadata` 描述剧本整体信息。
- `chapters` 保留小说来源结构，方便追踪每场戏来自哪些章节。
- `characters` 和 `locations` 作为全局索引，避免场景中重复写人物和地点。
- `events` 保存小说事实层，避免直接从小说跳到剧本导致情节丢失。
- `scenes` 是剧本主体。
- `adaptation_notes` 说明保留、改写和后续打磨建议，体现 AI 改编的可解释性。

## 5. 字段定义

### 5.1 metadata

```yaml
metadata:
  title: "示例剧本"
  source_type: "novel"
  language: "zh-CN"
  adaptation_type: "short_drama"
  generated_at: "2026-06-05 16:27:00"
```

字段说明：

- `title`：剧本标题。
- `source_type`：来源类型，当前固定为 `novel`。
- `language`：语言，中文项目使用 `zh-CN`。
- `adaptation_type`：改编方向，例如 `short_drama`。
- `generated_at`：生成时间。

设计原因：

`metadata` 让输出 YAML 成为独立文档，即使脱离系统页面，也能知道来源、语言、改编类型和生成时间。

### 5.2 chapters

```yaml
chapters:
  - id: "chapter_001"
    title: "第一章 初入会议室"
    order: 1
    word_count: 1280
```

字段说明：

- `id`：章节唯一标识。
- `title`：章节标题。
- `order`：章节顺序。
- `word_count`：章节字数。

设计原因：

小说改编必须能追踪来源章节。`chapters` 不保存全文正文，避免 YAML 过长；只保留章节元信息和引用 ID。

### 5.3 characters

```yaml
characters:
  - id: "char_001"
    name: "林夏"
    aliases: ["小夏"]
    role: "protagonist"
    description: "刚进入项目组的新人。"
    goal: "证明自己的方案可行。"
```

字段说明：

- `id`：人物唯一标识。
- `name`：人物姓名。
- `aliases`：别名列表。
- `role`：人物功能，例如 `protagonist`、`supporting`、`antagonist`。
- `description`：人物简介。
- `goal`：人物在剧情中的目标。

设计原因：

中文小说常有称呼变化，例如姓名、昵称、职务称呼。`aliases` 可以承载别名，`id` 保证场景和对白引用稳定。

### 5.4 locations

```yaml
locations:
  - id: "loc_001"
    name: "会议室"
    description: "公司内部会议室。"
```

字段说明：

- `id`：地点唯一标识。
- `name`：地点名称。
- `description`：地点说明。

设计原因：

地点独立成表后，场景只需要引用 `location_id`，避免同一地点在多个场景中反复描述不一致。

### 5.5 events

```yaml
events:
  - id: "event_001"
    source_chapter: "chapter_001"
    summary: "林夏被要求解释失败方案。"
    conflict: "新人方案受到质疑。"
    emotional_shift: "从紧张转向主动争取。"
    characters: ["char_001", "char_002"]
```

字段说明：

- `id`：事件唯一标识。
- `source_chapter`：来源章节。
- `summary`：事件摘要。
- `conflict`：事件冲突。
- `emotional_shift`：情绪变化。
- `characters`：参与人物 ID。

设计原因：

`events` 是小说事实层，位于章节和剧本场景之间。它能降低模型直接改写时产生幻觉或遗漏主线的风险。

### 5.6 scenes

```yaml
scenes:
  - id: "scene_001"
    source_chapters: ["chapter_001"]
    heading:
      location_id: "loc_001"
      time_of_day: "morning"
    purpose: "建立主角困境"
    conflict: "主角被质疑能力"
    characters: ["char_001", "char_002"]
    elements:
      - type: "action"
        text: "林夏推开会议室的门。"
      - type: "dialogue"
        character_id: "char_001"
        text: "我会证明这个方案可行。"
      - type: "narration"
        text: "空气短暂地安静下来。"
```

字段说明：

- `id`：场景唯一标识。
- `source_chapters`：来源章节列表。
- `heading`：场景头信息。
- `heading.location_id`：地点 ID。
- `heading.time_of_day`：时间段。
- `purpose`：场景戏剧目的。
- `conflict`：场景冲突。
- `characters`：出场人物 ID。
- `elements`：场景正文元素。

设计原因：

剧本主体按场景组织，符合影视和短剧创作习惯。`purpose` 和 `conflict` 是为 AI 改编额外加入的字段，能帮助创作者判断每场戏是否有明确功能。

### 5.7 scene elements

当前支持的场景元素类型：

```yaml
type: "action"
type: "dialogue"
type: "narration"
type: "transition"
type: "sound"
type: "shot"
```

字段说明：

- `action`：动作或场面描述。
- `dialogue`：人物对白，通常需要 `character_id`。
- `narration`：旁白或说明。
- `transition`：转场。
- `sound`：声音提示。
- `shot`：镜头说明。

设计原因：

Fountain 和传统剧本格式都区分场景标题、动作、角色对白和转场。本项目进一步保留 `narration`、`sound`、`shot`，是为了适配中文短剧、广播剧和后续分镜扩展。

### 5.8 adaptation_notes

```yaml
adaptation_notes:
  retained:
    - "保留主角进入职场后的核心冲突。"
  changed:
    - "将大段心理描写改为动作和对白。"
  next_steps:
    - "建议人工补充人物口吻差异。"
```

字段说明：

- `retained`：保留内容。
- `changed`：改写内容。
- `next_steps`：后续打磨建议。

设计原因：

小说转剧本不是逐字转换，AI 必然会压缩、合并和改写。`adaptation_notes` 用来解释这些变化，降低用户对生成结果的不确定感。

## 7. 校验规则

系统当前使用 `backend/schema.json` 执行结构校验，主要规则包括：

- 顶层必须包含 `schema_version`、`metadata`、`chapters`、`characters`、`locations`、`events`、`scenes`、`adaptation_notes`。
- `chapters` 至少包含 3 项，以体现题目对 3 个章节以上小说输入的硬性要求。
- `characters`、`locations`、`events`、`scenes` 至少包含一项。
- `scene.elements[].type` 只能是 `action`、`dialogue`、`narration`、`transition`、`sound`、`shot` 之一。
- `heading.time_of_day` 只能是 `dawn`、`morning`、`day`、`afternoon`、`evening`、`night` 之一。
- `chapter.order` 和 `chapter.word_count` 必须是数字。
- 每个场景必须包含 `heading`、`purpose`、`conflict`、`characters`、`elements`。

后端还会执行业务一致性校验：

- 场景引用的 `location_id` 必须存在于 `locations`。
- 对白引用的 `character_id` 必须存在于 `characters`。
- 每个场景至少应包含 3 个剧本元素。

## 8. 为什么不直接使用 Fountain

Fountain 很适合写剧本，但它是线性纯文本格式，不适合承载以下信息：

- 小说来源章节 ID。
- 人物别名和人物目标。
- 地点索引。
- 事件事实层。
- 场景与章节、事件的映射关系。
- 自动校验和引用一致性检查。

因此，本项目没有直接输出 Fountain，而是将 Fountain 的剧本元素思想结构化到 YAML 中。

## 9. 为什么不直接使用 ScreenJSON

ScreenJSON 更完整，也更接近工业级结构化剧本数据模型。但本项目的交付周期短，输入源是小说章节，目标是给作者快速获得可编辑初稿。完全照搬 ScreenJSON 会引入过多字段，增加生成和编辑成本。

因此，本项目采用轻量版本：

- 保留结构化数据思想。
- 保留人物、地点、场景、元素等核心概念。
- 增加小说改编特有的 `chapters`、`events`、`adaptation_notes`。
- 暂不引入复杂排版、修订、注释、制片拆解字段。

## 10. 后续扩展方向

后续版本可以在不破坏当前结构的基础上扩展：

- `acts`：增加幕/集结构，适配短剧分集。
- `beats`：增加节拍，细化剧情推进。
- `source_spans`：记录原文片段位置，实现原文到剧本追踪。
- `revision_history`：记录人工编辑和 AI 重写历史。
- `export_profiles`：支持导出 Fountain、Markdown、PDF 或 FDX。
- `quality_scores`：记录结构完整度、对白占比、场景冲突强度等评分。

## 11. 总结

Novel2Script 的 YAML Schema 不是行业既有标准，而是面向“中文小说转结构化剧本初稿”的项目级 Schema。它借鉴 Fountain 的剧本元素划分和 ScreenJSON 的结构化数据思想，同时保留小说改编所需的章节、事件和改编说明。

这种设计能满足本实训题目的核心要求：输入 3 个章节以上小说文本，输出可编辑、可校验、可进一步打磨的 YAML 剧本初稿，并能清楚说明 Schema 的设计原因。
