# 剧本初稿质量诊断与自动修复规划

文档版本：v2.1（比赛收敛版）  
原始版本：v1.0，2026-06-06  
更新时间：2026-06-07 14:28  
适用项目：Novel2Script，AI 小说转剧本工具  
项目周期：三天暑期实训  

## 1. 文档定位

本项目不在三天内尝试建立行业级、客观的剧本评分标准。本次比赛只实现一套能够实际运行和演示的：

> **AI 剧本初稿质量诊断与自动修复机制**

该机制用于回答三个核心问题：

1. 生成的 YAML 是否结构合法、引用有效？
2. 剧本初稿是否覆盖原文并具备基本改编可用性？
3. 系统能否定位主要问题，并自动修复问题场景？

文档分为两部分：

- **第一部分：本次比赛 MVP**，属于当前必须完成和验收的范围。
- **第二部分：未来规划**，记录受时间、样本和专业资源限制而暂缓的能力。

---

# 第一部分：本次比赛 MVP

## 2. MVP 目标

本次比赛交付以下完整闭环：

```text
Writer 生成 YAML 剧本
  -> Validator 硬性校验
  -> 计算四项确定性指标
  -> AI 进行三项初稿诊断
  -> 定位问题场景并给出建议
  -> 高严重度问题触发局部修复
  -> 重新校验并保存修复记录
```

MVP 的重点不是评分维度数量，而是保证链路真实、结果可解释、修复过程可展示。

## 3. 核心设计原则

### 3.1 合规与质量分离

YAML、Schema 和引用是否合法属于硬性门槛，不计入 AI 分数。硬性校验失败的结果不得标记为 `completed`。

### 3.2 规则指标与 AI 诊断分离

规则指标由程序确定性计算；AI 负责判断忠实度、可演性及人物对白问题。前端分别展示，避免用一个总分掩盖具体问题。

### 3.3 问题必须可定位

AI 发现的问题至少包含：

- 严重度。
- 问题类型。
- 场景 ID。
- 问题说明。
- 修改建议。

来源章节和事件 ID 在能够可靠获得时一并返回，但不作为本轮强制验收条件。

### 3.4 诊断必须服务于修复

高严重度问题必须能够生成明确的 `rewrite_scope`，Writer 只修改问题场景及必要引用，不重新执行完整工作流。

## 4. 第一层：硬性校验

硬性校验不参与评分。任一关键项失败，系统进入自动修复；两轮后仍失败则项目状态为 `failed`。

### 4.1 YAML 与 Schema

- YAML 文本能够解析。
- 顶层结构为对象。
- 符合 `backend/schema.json`。
- 章节数量不少于 3。
- 每个场景至少包含 3 个剧本元素。
- 必填字段、ID 格式和枚举值合法。

### 4.2 引用一致性

- 场景地点存在于地点表。
- 场景来源章节存在于章节表。
- 场景人物存在于人物表。
- 对白人物存在于人物表。
- 对白人物属于当前场景人物。
- 事件来源章节存在于章节表。
- 场景元素引用的事件存在于事件表。

### 4.3 最低可用性

- 至少存在一个人物、地点和关键事件。
- 每个场景包含动作或对白等可执行元素。
- 最终 YAML 能够被系统重新读取和校验。

### 4.4 校验结果

```json
{
  "schema_valid": true,
  "reference_valid": true,
  "errors": [],
  "severity_counts": {
    "high": 0,
    "medium": 0,
    "low": 0
  }
}
```

## 5. 第二层：四项确定性指标

MVP 只保留当前能够稳定计算和解释的四项指标。

| 指标 | 计算方式 | 作用 |
|---|---|---|
| 章节覆盖率 | 被场景引用的章节数 / 总章节数 | 发现整章遗漏 |
| 事件覆盖率 | 被剧本元素引用的事件数 / 总事件数 | 发现关键事件未进入剧本 |
| 引用一致性 | 有效引用数 / 全部受检引用数 | 发现悬空或错误 ID |
| 场景完整率 | 至少含 3 个元素的场景数 / 总场景数 | 发现过于单薄的场景 |

这些指标以百分比展示，不合成为所谓“客观剧本总分”。

以下数据可以作为辅助信息显示，但不参与通过决策：

- 对白占比。
- Schema 状态。
- 修复轮数。
- 高、中、低严重度问题数量。

### 5.1 指标限制

- 章节和事件 ID 被引用，不代表内容一定被高质量改编。
- 不同题材的合理对白比例不同，不设置统一合格区间。
- 指标异常用于触发检查，不能单独证明剧本艺术质量较差。

## 6. 第三层：三项 AI 初稿诊断

MVP 将 AI 评价收敛为三个最直接影响小说改编可用性的维度。

| 维度 | 建议权重 | 检查内容 |
|---|---:|---|
| 改编忠实度 | 40% | 是否保留主要事实、人物关系、主线冲突，是否出现明显幻觉 |
| 场景可演性 | 35% | 是否具有动作、对白、目的和冲突，是否只是小说摘要 |
| 人物与对白一致性 | 25% | 人物行为、对白归属和表达是否前后一致，是否明显模板化 |

```text
ai_draft_score =
  fidelity * 0.40
+ performability * 0.35
+ character_dialogue_consistency * 0.25
```

该分数统一命名为 **AI 初稿评分**，只用于当前模型下的问题诊断和修复前后对比，不宣传为行业标准或客观艺术评分。

### 6.1 改编忠实度

重点检查：

- 是否新增原文不存在的关键情节。
- 是否改变主要人物关系、身份或动机。
- 是否遗漏主线冲突。
- 是否将心理活动合理转化为动作或对白。

### 6.2 场景可演性

重点检查：

- 场景是否有明确目的和冲突。
- 是否存在可观察、可表演的动作。
- 对白和动作是否推动情节。
- 是否存在大量摘要式旁白。
- 场景是否过于模板化。

### 6.3 人物与对白一致性

重点检查：

- 人物行为是否符合已知身份和目标。
- 对白归属是否正确。
- 对白人物是否掌握相应信息。
- 同一人物前后表达是否明显矛盾。
- 是否大量使用通用模板句。

## 7. AI 问题输出

MVP 不要求 AI 为每个判断提供复杂原子事实链，但必须把问题定位到可修改范围。

```json
{
  "ai_draft_score": 78,
  "scores": {
    "fidelity": 82,
    "performability": 74,
    "character_dialogue_consistency": 76
  },
  "issues": [
    {
      "severity": "high",
      "type": "fidelity",
      "scene_id": "scene_003",
      "message": "该场景改变了主要人物作出决定的原因",
      "suggestion": "依据第二章事件重新编写人物决定前的动作和对白",
      "rewrite_scope": ["scene_003"]
    }
  ]
}
```

严重度定义：

| 严重度 | 定义 | 处理方式 |
|---|---|---|
| `high` | 影响结构合法、主线事实或人物关系 | 触发自动修复 |
| `medium` | 影响场景质量，但不妨碍初稿继续编辑 | 展示警告和建议 |
| `low` | 局部表达或风格问题 | 交由用户人工打磨 |

## 8. 通过与状态规则

MVP 不使用未经标定的 `85/70` 阈值判定“高质量”或“不合格”。

| 条件 | 项目状态 | 处理方式 |
|---|---|---|
| Schema 或引用失败 | 修复中 | Writer 局部修复 |
| 两轮后 Schema 或引用仍失败 | `failed` | 保存错误和最后结果 |
| Schema 合法但仍有 AI 高严重度问题 | `completed_with_warnings` | 保存结果并提示人工检查 |
| Schema 合法且无 AI 高严重度问题 | `completed` | 展示完整结果 |

AI 初稿评分用于展示和修复前后对比，不单独决定项目失败。

## 9. 自动修复闭环

### 9.1 修复范围

MVP 只实现 Writer 局部修复，不因一般质量问题重跑 Reader 和 Planner。

Writer Repair 输入：

- 当前剧本。
- Planner 事实层。
- Schema 和引用错误。
- AI 高严重度问题。
- `rewrite_scope`。

### 9.2 修复规则

- 最多修复两轮。
- 只修改问题场景及必要引用。
- 每轮修复后重新生成 YAML。
- 每轮重新执行 Schema、引用和 AI 检查。
- 保存修复前后剧本、校验结果和问题列表。
- 修复后不得引入新的 Schema 或引用错误。

### 9.3 修复结果展示

前端至少展示：

- 是否触发修复。
- 修复轮数。
- 修复原因。
- 修复前后 Schema 状态。
- 修复前后主要指标。
- 仍未解决的问题。

## 10. MVP 数据结构

评分和诊断结果保存在 `quality_metrics.json`，不写入最终剧本 YAML。

```json
{
  "schema_valid": true,
  "chapter_coverage": 1.0,
  "event_coverage": 0.86,
  "reference_consistency": 1.0,
  "scene_completeness": 0.92,
  "dialogue_ratio": 0.41,
  "validator_ai_score": 78,
  "ai_scores": {
    "fidelity": 82,
    "performability": 74,
    "character_dialogue_consistency": 76
  },
  "severity_counts": {
    "high": 0,
    "medium": 2,
    "low": 1
  },
  "repair_triggered": true,
  "repair_count": 1
}
```

实现时可以兼容当前已有字段，不要求为了文档示例立即进行破坏性数据迁移。

## 11. MVP 前端展示

质量面板分为四个区域：

1. **结构状态**：Schema 通过或失败。
2. **规则指标**：章节覆盖、事件覆盖、引用一致、场景完整。
3. **AI 初稿诊断**：三项分数和问题严重度。
4. **修复记录**：修复原因、轮次和前后变化。

问题列表显示：

- 严重度。
- 场景编号。
- 问题描述。
- 修改建议。

不在 MVP 中制作复杂雷达图，也不使用“行业级评分”等表述。

## 12. MVP 验收标准

### 12.1 自动化验收

- YAML 解析和 Schema 校验有测试覆盖。
- 少于 3 章的结构无法通过 Schema。
- 少于 3 个元素的场景无法通过 Schema。
- 人物、地点、章节和事件错误引用能够被发现。
- 四项确定性指标使用固定样本可重复计算。
- 自动修复最多执行两轮。
- 修复后重新执行 Schema 和引用校验。
- 无 API Key 时离线示例仍可完整展示。

### 12.2 演示验收

- 固定原创样例能够完成 Reader、Planner、Writer、Validator 全流程。
- Agent Trace 能区分真实模型调用和规则降级。
- 前端能展示完整剧本、规则指标和 AI 问题。
- AI 问题能够定位到具体场景。
- 至少准备一个可触发自动修复的演示案例。
- 页面能够展示修复前后结果。

### 12.3 人工快速检查

比赛前由开发者对固定样例进行一次人工核对：

- 主线是否基本保留。
- 人物关系是否出现明显错误。
- 场景是否具备基本动作和对白。
- 自动修复是否解决目标问题。

这属于演示质量检查，不宣称为专业评价者标定。

## 13. MVP 明确不做

本次比赛不实现或不承诺：

- 行业级剧本评分标准。
- 20-30 个样本的统计标定。
- 多名专业评价者独立评分。
- AI 与人工评分相关性分析。
- 误报率和漏报率统计。
- 六维以上的复杂专业量表。
- 复杂事件因果图。
- 人物完整弧光建模。
- 对白人物声纹量化。
- 主题、原创性和商业价值评分。
- 按题材分别训练或标定阈值。
- AI 评分决定作品是否具有艺术价值。

# 第二部分：未来规划

## 14. 未来定位

比赛结束后，如果继续产品化，可将当前 MVP 逐步升级为更可靠的“剧本初稿质量诊断平台”。未来规划不属于本次比赛验收范围。

## 15. 专业评价维度扩展

将当前三项 AI 诊断扩展为：

| 维度 | 参考权重 |
|---|---:|
| 改编忠实度 | 25% |
| 因果连贯性 | 20% |
| 场景戏剧性与可演性 | 20% |
| 人物一致性与弧光 | 15% |
| 对白自然度与人物声纹 | 15% |
| 节奏与转场 | 5% |

扩展维度需要配套明确评分锚点，不能只增加提示词中的评价名词。

## 16. 事实证据与语义覆盖

未来可增加：

- 将忠实度拆成原子事实逐项核验。
- 每个 AI 问题附带原文章节、事件和证据摘要。
- 区分事件 ID 引用和事件内容的语义实现。
- 为 AI 判断增加置信度。
- 置信度低时转为人工复核，不自动重写。

## 17. Planner 事实层增强

为事件增加重要度和改编策略：

```yaml
events:
  - id: event_001
    importance: 5
    adaptation_action: retain
  - id: event_002
    importance: 2
    adaptation_action: merge
  - id: event_003
    importance: 1
    adaptation_action: omit
    omission_reason: "与主线重复，压缩篇幅"
```

未来支持：

- `retain`：保留。
- `merge`：合并。
- `compress`：压缩。
- `omit`：有理由地省略。
- 事件因果关系图。
- 主要人物初始状态、目标、障碍、关键转变和最终状态。
- 重要度加权事件覆盖率。

这些能力用于解决“机械追求每章、每个事件全部出现”的问题。

## 18. 自动修复能力扩展

未来根据问题类型路由到不同 Agent：

| 问题 | 责任 Agent |
|---|---|
| 章节边界或事实错误 | Reader |
| 关键事件、人物关系或因果链缺失 | Planner |
| YAML、字段或引用错误 | Writer |
| 场景目标、冲突或动作薄弱 | Writer |
| 对白模板化或人物声音趋同 | Writer |
| 严重幻觉或人物关系改变 | Planner + Writer |
| 判断证据不足 | Validator 或人工复核 |

同时增加：

- 修复版本回退。
- 修复前后语义差异。
- 目标问题改善检测。
- 防止修复其他指标时发生质量退化。

## 19. 人工标定与统计评测

在产品需要公开宣称评分可靠性时，再进行以下工作：

- 准备 20-30 个以上不同题材、长度和质量等级的样本。
- 邀请 2-3 名具有剧本阅读或创作经验的评价者独立评分。
- 使用统一量表并记录评价者一致性。
- 比较 AI 分数和人工评分的相关性。
- 统计高严重度问题的准确率、误报率和漏报率。
- 根据数据调整权重、锚点、阈值和提示词。
- 固定模型、温度、评分提示词和评分版本。

在完成标定前，不使用固定 `85/70` 阈值对作品作“高质量/不通过”的绝对判断。

## 20. 长期验收指标

- 同一固定输入的 AI 分项评分波动处于可接受范围。
- AI 问题均能定位到场景并提供来源证据。
- 高严重度问题经人工抽查具有可接受准确率。
- AI 与人工评价具有可解释的相关性。
- 自动修复后目标问题改善，其他关键指标不退化。
- 不同题材使用适合自身的评价基线。

## 21. 当前限制

- AI 评分受模型、提示词、上下文长度和随机性影响。
- 文学改编不存在唯一正确答案。
- 忠实度、戏剧性和篇幅压缩之间存在天然权衡。
- 规则覆盖率只能发现风险，不能评价艺术质量。
- 短篇样例的结果不能直接推广到长篇和不同剧本类型。
- 自动诊断不能替代专业编剧或编辑的整体判断。

## 22. 对外表述

本次比赛推荐使用：

> Novel2Script 内置剧本初稿质量诊断与自动修复机制，能够检查 YAML 结构和引用完整性，计算覆盖指标，并由 Validator Agent 定位忠实度、可演性及人物对白问题。系统可针对高严重度问题进行最多两轮局部修复。

不建议使用：

- “行业标准剧本评分系统”
- “客观评价剧本艺术质量”
- “AI 分数等同专业编剧评分”
- “评分已通过大规模人工验证”

## 24. 总结

本次比赛优先证明四件事：

1. 生成结果结构合法。
2. 关键内容覆盖情况可量化。
3. AI 能定位影响初稿使用的问题。
4. 系统能完成可展示的局部修复闭环。

专业评分扩展、人工标定和统计验证全部放入未来规划。这样能够控制三天项目的交付风险，同时保留清晰、可信的产品演进方向。
